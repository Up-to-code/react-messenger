ما الذي نستطيع فعله الآن؟

النسخة الحالية تقدم واجهة عربية، خيارات منتجات مستقلة، مقارنة وفلاتر، اختيار ألوان ومساحة، توصيل وإضافات، بيانات عميل محلية، مراجعة وتأكيد طلب، ثم محاكاة دفع وإيصال محفوظ. أضيف اتصال OpenRouter وخدمة CrewAI فعلية تضم مستشار تجارة ومراجعًا للمخرجات. التشغيل الافتراضي تجريبي؛ جودة الاستدلال الحي لم تُختبر بمفتاح مدفوع.

هذا التقرير يجمع ما تقوله المصادر مع توصيات تصميم خاصة بالمشروع. كل توصية وخطة تنفيذ أدناه هي استنتاج هندسي، وليست قدرة مضافة لمجرد وجود المرجع.

الهيكل المقترح للتجارة الكاملة

طلب العميل ← فهم النية والقيود ← بحث الكتالوج ← مقارنة واختيار ← تسعير ومخزون ← توصيل ← مراجعة ← تفويض العميل ← دفع ← تأكيد موثوق ← تتبع وخدمة ما بعد الشراء

الوكيل يفسر الطلب ويقرر السؤال التالي أو نوع الاختيار. خدمة التجارة تحسب السعر والضرائب والمخزون والتوصيل. واجهة المستخدم تعرض مكونات معروفة وفق بيانات منظمة، دون تنفيذ HTML أو شيفرة ينتجها النموذج. أرقام SKU، معرف جلسة الشراء وإصدار عرض السعر منفصلة عن معرف رسالة المحادثة.

إعداد الطلب يمكن أن يستمر تلقائيًا حتى اكتمال التفاصيل. للشراء الفعلي يلزم تفويض محدد بالسلة والسعر النهائي والشحن قبل الإتمام، ثم تأكيد من خدمة الدفع أو حدث موثوق. عند انتهاء مهلة الطلب نستعلم عن حالته قبل إعادة التنفيذ؛ لا نفترض أنه فشل ولا نكرر الخصم. هذا تصميم مقترح مستنتج من جلسات الشراء والمدفوعات في ACP ومن فصل القدرات في UCP.

الطلب العام والطلب المحدد

رسالة العميلالقرار الصحيحالواجهة
«عايز جهاز للشغل»سؤال واحد عن الاستخدام أو الميزانية؛ لا تعرض استمارة طويلة.خيارات استخدام، ثم توصيات.
«سماعات أزرق، أقل من ٢٠٠ دولار»البحث مباشرة بالقيود المعروفة؛ لا تعيد سؤال اللون أو الميزانية.منتجات مطابقة، أو شرح عدم وجود تطابق وخيارات تعديل واضحة.
«زي اللي اخترته قبل كده لكن أرخص»استرجاع الاختيار بمعرف المصدر، ثم تحديد أي قيود تغيرت.مقارنة الاختيار السابق بالبدائل.
«خد لي الاتنين، بس واحد بس للتوصيل»فصل العناصر والكميات والتوصيل؛ سؤال توضيحي عندما لا يمكن تحديد المقصود.سلة متعددة العناصر ومجموعات شحن؛ هذه قدرة غير موجودة بعد.
«غيرت رأيي، عايز استلام»تحديث طريقة الاستلام وإعادة السعر والتاريخ وإلغاء صلاحية مراجعة سابقة تغير إجماليها.خيارات استلام ثم ملخص محدث.

احفظ القيود مع مصدرها: قيمة مؤكدة من العميل، قيمة مستنتجة تحتاج تأكيدًا، أو قيمة غير معروفة. عند التعارض استخدم آخر اختيار صريح دون حذف تاريخ التغيير. اقتراح عملي: سجل نية يتضمن intent، constraints، missing_fields، next_action وsource_message_ids، وتتحقق منه الخدمة قبل تنفيذ أي أثر تجاري.

هل يمكن استخدام ChatGPT؟

نعم، يمكن استخدام نموذج OpenAI عبر API للفهم والتلخيص واختيار الوظائف. محادثة ChatGPT الشخصية لا تصبح تلقائيًا ذاكرة التطبيق. التطبيق يحتفظ بالمحادثات ويختار السياق المرسل؛ وتوضح وثائق حالة المحادثة طرق إدارة الحالة بين الطلبات. اتصال OpenRouter يتيح اختيار نموذج متوافق، وخدمة Crew الحالية تستخدمه، لكن يلزم مفتاح ونموذج يدعمان الوظائف المطلوبة. أسماء النموذج وقدراته وتكلفته تعتمد على الاختيار الفعلي.

لا يكفي توجيه النموذج بكلمة «كن مستقلاً». الاستقلالية المفيدة تحتاج أدوات موثوقة، حالة عمل محفوظة، ميزانية للوقت والمحاولات، ونتائج قابلة للتحقق. المراجع الحالي يراجع المخرجات قبل العرض؛ لا يجعله ذلك نظام تجارة إنتاجيًا.

المحادثات الطويلة دون فقدان السجل

افصل أربعة أشياء: سجل كامل، حالة الطلب، ذاكرة تفضيلات العميل، وسياق الطلب الحالي. ذاكرة داخل المحادثة تختلف عن الذاكرة الممتدة بين المحادثات؛ تعرض وثائق LangChain هذا الفصل وتناقش تقليص الرسائل والتلخيص. ضغط السياق يحل تكلفة الإدخال، وليس حفظ السجل.

  1. كل رسالة لها معرف ثابت، دور، وقت ومصدر. يحتفظ SQLite بالأقدم عند حفظ الرسائل الجديدة.
  2. السياق الحالي يثبت آخر اختيارات وتفضيلات وطلب، ويضيف رسائل حديثة وحقائق أو نتائج بحث من الأرشيف بمعرفاتها.
  3. واجهة الأرشيف تعرض مقتطفات مطوية، بحثًا وتحميلًا للأقدم. اختيار محادثة موجودة بالخادم فقط يعيد آخر ٥٠ رسالة نصية.
  4. في النسخة الحالية الملخص استخراجي والبحث بالكلمات؛ الصور والمكونات التفاعلية الأصلية تبقى في IndexedDB. لا توجد ذاكرة دلالية شاملة أو مزامنة حسابات بعد.
  5. الخطوة التالية: ملخص دلالي بإصدار وحد آخر رسالة لخصها النموذج، وحقائق موثقة بمعرف مصدر وتاريخ انتهاء، مع إمكانية استرجاع النص الأصلي قبل أي قرار حساس.
  6. حدد ميزانية السياق بالرموز وفق النموذج الفعلي. توفر OpenAI ضغط سياق، لكنه لم يُفعّل في هذا المشروع ولا يحل محل قاعدة البيانات.

مثال تقييم: العميل يقول ميزانيته في الرسالة ٣، يغير الموضوع ٦٠ مرة، ثم يطلب «اختار المناسب». يجب استرجاع الميزانية مع مصدرها والتحقق من عدم تغيرها، وإبقاء كل الرسائل قابلة للقراءة.

اختيارات حسب الموقف

الاختيارات ليست استطلاعًا واحدًا يتكرر: المنتج بطاقات، المقارنة جدول، اللون علامات فوق دوائر صغيرة، مساحة الجهاز خيارات نصية، التوصيل راديو، الإضافات مربعات اختيار، تفضيلات عامة بطاقة أفعال، والاستطلاع تصويت مستقل. النموذج يختار الوظيفة والمحتوى ضمن مخطط؛ كل رد اختيار يعود كرسالة جديدة مع معرف مصدره.

المتاح: show_choices لاختيار واحد أو عدة خيارات، create_poll لتصويت، بالإضافة إلى أدوات المنتجات والفلاتر والمقارنة والرسائل المتعددة والمراجع وجمع بيانات الطلب. أدوات الواجهة تنهي الدور الحالي؛ الأدوات التجارية متعددة الخطوات ليست منفذة بعد. إضافة عنصر واجهة جديد تتطلب مخططًا ومكونًا وطريقة تحقق وأثرًا واضحًا في المحادثة.

تاريخ الوصول: سياسة العمل أولًا

التقدير الحالي تلقائي من مدة التحضير، ساعة الإغلاق، المنطقة الزمنية، أيام العمل والعطلات المحجوبة. التغيير اليدوي اختياري بتقويم خاص. القواعد الحالية أمثلة للقاهرة: أيام الأحد–الخميس، حد الطلب ١٤:٠٠، وتجهيز يوم أو يومين بحسب الطريقة، وليست وعد شحن.

المطلوب للإنتاج: موقع المخزن، التوفر، عنوان العميل ومنطقة التوصيل، وقت تعبئة المنتج، الناقل وسعته، مجموعات شحن السلة، أوقات القطع والعطل. استعلم من خدمة التنفيذ واعرض نطاقًا وسببًا قابلًا للتفسير. لا تدع النموذج يخترع التاريخ. إذا كان اختيار الموعد إلزاميًا لبعض الأنشطة، يلزم تطبيق شرط اختيار صريح؛ الوضع الحالي اختياري.

خطة تنفيذ وتقييم

  1. المرحلة الأولى: تثبيت عقد بيانات للسلة والطلب، واختيار مصدر متجر تجريبي حقيقي. تنفيذ البحث والتسعير والمخزون كوظائف مستقلة عن النموذج.
  2. الثانية: حالات شراء محفوظة وربط جلسة دفع اختبارية وأحداث الطلب؛ الانقطاع أو إعادة التحميل لا ينشئ طلبًا ثانيًا.
  3. الثالثة: تلخيص بإصدارات، استرجاع عربي، ذاكرة تفضيلات لها مدة صلاحية، وواجهة تصحيح ما يتذكره المساعد.
  4. الرابعة: التتبع والإلغاء والمرتجعات، تقييم جودة عربي ومراقبة تكلفة وزمن كل طلب.

مجموعة التقييم المقترحة: طلب عام، طلب بقيود كاملة، قيود متناقضة، منتج غير متوفر، تغيير لون بعد التسعير، سلة متعددة، عنوان خارج النطاق، انقطاع عند الدفع، رسالة سابقة محذوفة من نافذة السياق، أمر داخل وصف منتج يحاول تغيير قواعد الوكيل، واسترجاع بعد محادثة طويلة. معايير النجاح: صحة القيود، عدد الأسئلة غير الضرورية، مصدر كل معلومة، عدم تكرار الدفع، عدم اختراع مخزون، استرجاع المصدر، وزمن وتكلفة الإنجاز.

تغطية الاختبارات الحالية تشمل حفظ SQLite وعزل المتصفحات، ٦٠٠ رسالة دون حذف الأقدم، استدعاءات مزود مجزأة أو غير مكتملة، مخرجات Crew الحقيقية باستخدام نموذج بديل للاختبار، التقويم وقواعد الوصول، وواجهات الطلب بالعربية. هذه الاختبارات لا تثبت جودة نموذج مدفوع أو صلاحية متجر إنتاجي.
